Clustered Shading

타일에 깊이축을 더한 3D 클러스터 · Path Case Study

IMPLEMENTATION · CHAPTER 6 · RENDERING PATH

Clustered Shading — 화면 타일에 깊이(Z) 슬라이스를 더하다

광원이 수백 개인 장면을 효율적으로 그리는 길은 "이 픽셀에 실제로 닿는 광원만 계산하기"입니다. Forward+(타일드 포워드)는 화면을 2D 타일로 나눠 타일마다 영향 광원 리스트를 만들지만, 깊이 방향은 나누지 않아 한 타일 안에 가까운 표면과 먼 표면이 섞이면 둘 다에 영향 주는 광원이 전부 리스트에 들어갑니다. Clustered Shading은 여기에 Z 슬라이스를 더해 화면을 3D 클러스터 (예: 16×9×24)로 쪼개, 근/원 표면이 서로의 광원을 나눠 갖지 않게 합니다. 이 페이지에서는 왜 깊이 축이 필요한지(원리), 2D 타일 vs 3D 클러스터를 만지는 데모(개념), 클러스터 인덱싱 HLSL (구현)을 차례로 해부합니다.

규약 이 가이드는 D3D 규약으로 통일합니다: 행벡터 v' = v * M(HLSL mul(v, M)), 행렬 행 우선 저장, 왼손 좌표계, 클립 공간 z ∈ [0, 1], 텍스처 V축은 위→아래입니다. 클러스터 인덱싱은 뷰 공간 깊이(view-space Z)를 기준으로 하며, 좌표계가 무엇이든 "카메라로부터의 거리"라는 물리적 의미만 일관되면 슬라이스 공식 자체는 동일합니다.

1. 원리 — Forward+의 깊이 한계를 어떻게 깨나

직관부터 말하면 이렇습니다: 화면에서 같은 자리에 겹쳐 보여도, 카메라 코앞의 벽과 저 멀리 산은 서로 완전히 다른 광원의 영향을 받습니다. 그런데 화면을 2D 타일로만 나누면 이 둘이 같은 타일에 들어가고, 그 타일의 광원 리스트에는 코앞 벽에 닿는 광원과 먼 산에 닿는 광원이 전부 섞여 들어갑니다.

Forward+(타일드 포워드)는 화면을 예컨대 16×16 픽셀 타일로 나누고, 각 타일이 덮는 화면 사각형을 깊이 방향으로 무한히 뻗은 기둥(frustum sub-volume)으로 보고 그 기둥과 겹치는 광원을 리스트에 담습니다. 문제는 이 기둥이 near부터 far까지 길쭉하다는 것입니다. 타일 안에 가까운 표면(near)과 먼 표면(far)이 함께 보이면, near 근처에만 있는 광원도, far 근처에만 있는 광원도 모두 "이 기둥에 겹친다"고 판정되어 리스트에 들어갑니다. 정작 각 표면은 그중 일부에만 실제로 닿는데도요. 이것이 깊이 방향 false positive(가짜 양성)입니다 — "닿지 않는데 닿는다고 세는" 낭비죠.

Clustered Shading은 이 길쭉한 기둥을 깊이 방향으로 Z 슬라이스로 토막 냅니다. 화면 2D 타일(가로 X · 세로 Y) 격자에 깊이 슬라이스(Z)를 곱해, 화면을 3D 클러스터 격자(예: 16×9×24 = 3456개의 작은 절두체 조각)로 나눕니다. 이제 각 클러스터는 near~far 전체가 아니라 얇은 깊이 구간 하나만 담당하므로, 그 구간에 실제로 영향 주는 광원만 리스트에 들어갑니다. 코앞 벽 클러스터와 먼 산 클러스터는 서로의 광원을 나눠 갖지 않습니다.

직관 Forward+는 화면을 세로로 자른 유리창(2D 격자)이고, Clustered는 그 유리창을 깊이로도 잘라 만든 얼음 트레이(3D 격자)입니다. 광원이라는 물을 부으면, 유리창 칸은 앞뒤로 길어 한 칸에 여러 광원이 고이지만, 얼음 트레이 칸은 작아 각 칸에 최소한의 광원만 담깁니다.

1-1. 왜 깊이 슬라이스를 "로그"로 나누나

직관: 원근 투영에서는 가까울수록 화면상 크게, 멀수록 작게 보입니다. 그래서 near 근처의 얕은 깊이 변화가 화면에서는 큰 차이를 만들고, far 근처의 같은 깊이 변화는 거의 차이를 안 만듭니다. 깊이를 균등 간격으로 자르면 near 쪽에는 클러스터가 듬성듬성, far 쪽에는 촘촘하게 배치되어 정작 디테일이 몰린 near 쪽이 성기게 나뉩니다. 반대로 가까울수록 촘촘하게 나눠야 시각적으로 균형이 맞습니다.

그래서 깊이를 로그(지수) 분포로 나눕니다. 뷰 공간 깊이 z(양수, near≤z≤far)가 몇 번째 슬라이스에 속하는지는 이렇게 구합니다.

수식
slice(z) = floor( log(z / near) / log(far / near) × numSlices )
  • z / near — near를 기준(1.0)으로 정규화한 깊이. z = near면 1, z = far면 far/near.
  • log(z/near) / log(far/near) — 그 값을 0~1로 매핑하되, 로그라서 가까운 쪽이 넓게 펴집니다. 즉 near 근처의 얇은 깊이 구간이 0~1 스케일에서 큰 폭을 차지 → 슬라이스가 촘촘.
  • × numSlices 후 floor — 0 ~ (numSlices−1) 정수 슬라이스 인덱스로 양자화.

이 공식은 실무에서 보통 slice = floor( log(z) × A − B ) 꼴로 미리 상수 A = numSlices / log(far/near), B = numSlices × log(near) / log(far/near)를 CPU에서 계산해 두고 셰이더에서는 곱셈·뺄셈 한 번으로 끝냅니다. Doom 2016(id Tech 6)이 쓴 그 형태입니다.

2. 직관 데모 — 2D 타일 vs 3D 클러스터

아래는 절두체를 옆에서 본 단면(side view)입니다. 왼쪽에 카메라, 오른쪽으로 뻗는 사다리꼴이 시야 절두체이고, 세로선은 화면 타일 경계, 가로(깊이 방향) 곡선은 로그 간격 Z 슬라이스 경계입니다. 원은 광원의 영향 반경입니다. 각 클러스터 셀은 겹치는 광원 수만큼 붉게 물듭니다(히트맵).

슬라이스 = 1로 두면 깊이를 안 나눈 Forward+와 동일합니다(한 타일 기둥에 광원이 몰림). 슬라이스 수를 늘리면 셀이 잘게 쪼개지며 셀당 평균 광원 수가 줄어드는 것을 HUD로 확인하세요.

클러스터 준비 중…
세로선 = 화면 타일 경계 · 가로 곡선 = 로그 Z 슬라이스 경계 · 원 = 광원 영향 반경 · 셀 색 = 겹친 광원 수(히트맵). 슬라이스=1은 Forward+(깊이 미분할)와 같습니다.

3. Forward+ vs Clustered

항목Forward+ (2D 타일)Clustered (3D)
분할 차원 화면 2D (X·Y 타일) 화면 + 깊이 3D (X·Y·Z 클러스터)
깊이 false positive 큼 — 타일 기둥이 near~far로 길쭉해 근/원 광원이 한 리스트에 섞임 작음 — 얇은 깊이 구간만 담당해 실제 닿는 광원만
깊이 프리패스 대개 필요 — 타일별 min/max 깊이를 알아야 기둥을 조여 컬링 불필요(선택) — 클러스터 격자가 깊이와 무관하게 미리 구성 가능
광원 리스트 크기 타일당 리스트 (X·Y개) 클러스터당 리스트 (X·Y·Z개, 더 잘게)
적합 중간 규모 광원, 깊이 편차가 작은 씬 많은 광원 · 깊이 편차 큰 오픈월드 씬

핵심 트레이드오프: Clustered는 셀 수가 늘어나(3D) 컬링 계산·메모리가 조금 더 들지만, 깊이 프리패스 의존을 없애고 false positive를 줄여 광원이 많고 깊이 편차가 큰 씬에서 더 안정적입니다. 그래서 오픈월드의 사실상 표준이 되었습니다.

4. 구현 — 클러스터 인덱싱

구현의 심장은 두 가지입니다: (1) 화면 좌표 + 깊이 → 클러스터 인덱스를 구하는 함수, (2) 그 인덱스로 per-cluster 광원 리스트를 읽어 그 광원만 순회하는 픽셀 셰이더. 아래는 골격이지만 인덱싱 수식은 실제 그대로입니다(광원 컬링을 채우는 컴퓨트 패스, 데이터 구조 세부는 생략).

cluster_index.hlslhlsl
// 클러스터 격자 파라미터 (CPU에서 상수 버퍼로 업로드)
cbuffer ClusterParams : register(b0) {
    uint3  gridDim;      // 클러스터 격자 (예: 16, 9, 24)
    float  zNear;        // 절두체 근평면 거리 (양수)
    float2 tileSizePx;   // 타일 한 칸 픽셀 크기 (screenW/gridX, screenH/gridY)
    float  zFar;         // 절두체 원평면 거리
    float  _pad;         // 16바이트 정렬 맞춤(float3+float 규칙)
};

// per-cluster 광원 인덱스 리스트 (컴퓨트 컬링 패스가 프레임당 1회 채움)
struct LightGrid { uint offset; uint count; };      // 이 클러스터의 리스트 시작/개수
StructuredBuffer<LightGrid> gLightGrid   : register(t0);  // 클러스터당 1개
StructuredBuffer<uint>      gLightIndex  : register(t1);  // 평탄화된 광원 인덱스 배열

// (1) 화면 픽셀 좌표 + 뷰 공간 깊이 → 3D 클러스터 인덱스
uint ClusterIndex(float2 screenPx, float viewZ) {
    // 화면 X·Y 타일 인덱스: 픽셀 좌표를 타일 크기로 나눠 내림
    uint tileX = (uint)(screenPx.x / tileSizePx.x);
    uint tileY = (uint)(screenPx.y / tileSizePx.y);

    // 깊이 슬라이스: 로그(지수) 분포 — 가까울수록 촘촘
    //   slice = floor( log(z/near) / log(far/near) * numSlices )
    float zClamped = max(viewZ, zNear);              // near 아래로 내려가면 log 발산 → 클램프
    float slice    = log(zClamped / zNear) / log(zFar / zNear) * (float)gridDim.z;
    uint  sliceZ   = (uint)clamp(slice, 0.0, (float)(gridDim.z - 1));

    // 3D (tileX, tileY, sliceZ) → 1D 인덱스로 평탄화 (행 우선)
    //   idx = x + y*gridX + z*gridX*gridY
    return tileX + tileY * gridDim.x + sliceZ * gridDim.x * gridDim.y;
}

// (2) 픽셀 셰이더: 내 클러스터의 광원만 순회
float3 ShadePixel(float2 screenPx, float viewZ, float3 P, float3 N, float3 albedo) {
    uint      ci   = ClusterIndex(screenPx, viewZ);
    LightGrid cell = gLightGrid[ci];                 // 이 클러스터의 리스트 위치

    float3 lit = albedo * 0.03;                      // 앰비언트
    for (uint k = 0; k < cell.count; ++k) {          // 전체 광원이 아니라 '내 셀'의 광원만
        uint  li = gLightIndex[cell.offset + k];     // 평탄 배열에서 실제 광원 인덱스
        // Light L = gLights[li];  ... 블린-퐁 등으로 조명 누적 ...
        lit += ShadeOneLight(li, P, N, albedo);
    }
    return lit;
}

4-1. 타일 인덱스 — 픽셀을 타일 크기로 나누기

tileX = screenPx.x / tileSizePx.x는 화면 픽셀 X를 타일 한 칸 폭으로 나눠 내림한 값입니다. 화면 폭이 1920, 격자 X가 16이면 타일 폭은 120픽셀이고, X=250인 픽셀은 250/120 = 2.08 → 2번 타일에 속합니다. Y도 동일합니다. 이 (tileX, tileY)가 Forward+와 똑같은 2D 타일 좌표입니다 — Clustered는 여기에 Z만 보탭니다.

4-2. 깊이 슬라이스 — 로그 인덱싱

slice = log(z/near) / log(far/near) * numSlices가 1-1에서 유도한 그 공식입니다. gridDim.z가 슬라이스 수(numSlices)이고, 결과를 floor(정수 캐스팅)해 슬라이스 인덱스로 만든 뒤 clamp(..., 0, gridDim.z-1)로 far를 살짝 넘는 픽셀이 배열 밖으로 새지 않게 가둡니다. near 쪽이 촘촘, far 쪽이 성긴 분포가 이 한 줄에서 나옵니다.

4-3. 3D → 1D 평탄화 — x + y·gridX + z·gridX·gridY

GPU 버퍼는 1차원 배열이므로 (tileX, tileY, sliceZ) 3D 좌표를 하나의 인덱스로 접어야 합니다. idx = x + y*gridX + z*gridX*gridY는 행 우선(row-major) 평탄화입니다: X가 가장 빨리 변하고(연속), 한 행(gridX개)을 다 돌면 Y가 1 증가하고, 한 평면(gridX·gridY개)을 다 돌면 Z가 1 증가합니다. 컴퓨트 컬링 패스가 gLightGrid를 채울 때도 같은 공식으로 인덱스를 계산해야 픽셀 셰이더의 읽기와 짝이 맞습니다.

4-4. 광원 리스트 순회 — 전체가 아니라 "내 셀"만

gLightGrid[ci]는 이 클러스터가 담당하는 광원들이 평탄 배열 gLightIndex의 어디부터 (offset) 몇 개(count) 있는지 알려 줍니다. 픽셀 셰이더는 전체 광원 64/256/…개가 아니라 cell.count개(대개 한 자릿수)만 돌면 됩니다. 디퍼드의 for (i < NR_LIGHTS) 전수 순회를 "내 클러스터의 광원만"으로 좁힌 것이 Clustered의 성능 이점 그 자체입니다.

함정 near가 0이면 log(z/near)가 발산합니다(0으로 나누기 → −∞). 그래서 zNear는 반드시 양수여야 하고, 위 코드처럼 viewZ도 max(viewZ, zNear)로 클램프해야 near 앞쪽 픽셀이 음의 슬라이스로 튀지 않습니다. 또한 viewZ의 부호와 좌표계에 주의하세요 — 왼손 좌표계는 카메라 앞이 +Z라 깊이가 양수지만, 오른손(뷰 공간 −Z 앞)을 쓰던 코드를 이식하면 viewZ = -posView.z처럼 부호를 뒤집어 양의 거리로 만들어야 로그가 성립합니다.
성능 클러스터 컬링(광원↔클러스터 겹침 판정)은 프레임당 1회 컴퓨트 셰이더로 끝납니다. 광원이 아무리 많아도 픽셀 셰이더는 자기 클러스터의 몇 개만 돌므로 픽셀 조명 비용이 안정적입니다. 대신 격자를 잘게 쪼갤수록(예: 16×9×24 → 32×18×48) 클러스터 수가 세제곱으로 늘어 컬링 비용과 광원 리스트 메모리가 커집니다. 격자 해상도는 "false positive 감소"와 "컬링·메모리 비용" 사이의 흥정입니다. 실무는 24 슬라이스 안팎을 즐겨 씁니다.

5. 언제 쓰나 — 실무 노트

실무 Clustered는 많은 동적 광원 + 깊이 편차가 큰 오픈월드의 사실상 표준입니다. 대표 사례:
  • Emil Persson / Avalanche Studios — Just Cause 시리즈에서 "Clustered Shading"을 실전 도입해 널리 알린 작업.
  • Doom 2016 (id Tech 6) — clustered forward+. 로그 깊이 슬라이스 + 프레임당 1회 컴퓨트 컬링의 교과서적 구현.
  • Unreal Engine — Clustered 라이트 그리드로 다수 로컬 광원을 처리.
  • Detroit: Become Human (Quantic Dream) — 대규모 실내/동적 조명에 클러스터드 셰이딩 활용.
광원이 소수이거나 깊이 편차가 작은 씬이라면 Forward+로 충분합니다. "광원이 많고, 화면 한 픽셀 뒤로 near~far가 크게 벌어진다"가 Clustered를 택하는 신호입니다.
