IMPLEMENTATION · CHAPTER 6 · RENDERING PATH

Forward+ / Tiled Forward — 타일마다 영향 광원만 추린다

광원이 수백 개인 장면을 포워드(forward)로 그리면, 픽셀 셰이더마다 모든 광원을 반복문으로 돕니다. 대부분의 광원은 그 픽셀에서 멀어 기여가 0인데도 비용은 똑같이 들죠 — 비용이 픽셀 수 × 광원 수로 폭발합니다. Forward+ (Tiled Forward)는 여기에 딱 한 단계를 끼워 넣습니다: 렌더링 전에 화면을 작은 타일로 나누고, 각 타일에 실제로 닿는 광원 목록만 컴퓨트 셰이더로 미리 추려(light culling) 둡니다. 그러면 픽셀 셰이더는 자기 타일의 광원(평균 k개, k ≪ N)만 돌면 됩니다. 이 페이지에서는 그 라이트 컬링 컴퓨트 셰이더의 골격과, 그것을 읽어 도는 포워드 픽셀 셰이더를 구조와 함정 위주로 해부합니다.

규약 이 가이드는 D3D 규약으로 통일합니다: 행벡터 v' = v * M(HLSL mul(v, M)), 행렬 행 우선 저장, 왼손 좌표계, 클립 공간 z ∈ [0, 1], 텍스처 V축은 위→아래입니다. 컬링과 조명 계산은 모두 뷰 공간(view space)에서 이뤄집니다 — 카메라가 원점(0,0,0)이라 타일 절두체·거리 계산이 단순해집니다.

1. 원리 — forward의 O(P×N)을 어떻게 줄이나

한 문장으로: "픽셀마다 모든 광원을 도는 대신, 미리 타일별로 광원을 걸러 놓고 픽셀은 자기 타일 것만 돌게 하자." 이게 Forward+의 전부입니다.

평범한 포워드 렌더링에서 조명 비용은 대략 P × N입니다(P = 셰이딩한 픽셀 수, N = 광원 수). 광원 256개짜리 장면이라면 픽셀 하나마다 256번의 조명 계산이 들어갑니다 — 그 픽셀에서 255개가 너무 멀어 기여가 0이어도 말이죠. 명백한 낭비입니다.

Forward+는 렌더링 전에 한 단계를 추가합니다.

  1. 화면을 타일로 분할: 화면을 예컨대 16×16 px 타일 격자로 나눕니다. Full HD면 120 × 68 ≈ 8160개의 타일이 생깁니다.
  2. 라이트 컬링(light culling): 컴퓨트 셰이더가 타일마다 하나의 스레드 그룹을 맡아, 그 타일이 화면에서 차지하는 영역으로 절두체(frustum)를 만들고, 광원 N개를 훑어 그 절두체와 겹치는 광원만 per-tile 광원 목록에 담습니다.
  3. 포워드 셰이딩: 실제 지오메트리를 평소처럼 포워드로 그리되, 픽셀 셰이더는 자기 픽셀이 속한 타일의 광원 목록만 읽어 평균 k개만 돕니다.

그래서 조명 비용이 P × N에서 P × k(k = 타일 평균 영향 광원 수)로 줄어듭니다. 광원이 화면 곳곳에 흩어져 있으면 k는 N보다 훨씬 작아, 사실상 "픽셀당 실제로 닿는 광원만" 계산하게 됩니다. 여기에 컬링 패스 비용(타일 수 × N의 교차 검사)이 더해지지만, 컬링은 픽셀이 아니라 타일 단위라 훨씬 저렴합니다.

직관 비유하자면, 우편물을 온 도시에 다 돌리는 대신(포워드) 먼저 동네(타일)별로 분류해 두고 각 집(픽셀)엔 자기 동네 우편만 배달하는 것입니다. 분류(컬링)에 시간이 조금 들지만, 배달(셰이딩) 총량이 확 줄어듭니다.

절두체–구 교차로 컬링: 각 타일은 화면의 작은 사각형이고, 이 사각형을 카메라에서 밀어내면 좌·우·상·하 네 평면으로 둘러싸인 타일 절두체가 됩니다(근/원 평면까지 더하면 6평면). 점광원을 중심 + 반경의 구(sphere)로 보면, "이 광원이 타일에 영향을 주는가?"는 곧 구가 타일 절두체와 겹치는가?로 판정됩니다. 각 평면에 대해 구 중심의 부호거리(signed distance)가 −반경보다 크면 그 평면 안쪽 — 6평면을 다 통과하면 타일에 담습니다.

함정 타일 절두체는 깊이(z) 방향으로는 나뉘지 않습니다. 근/원 평면을 타일 안 픽셀들의 최소·최대 깊이로 좁히더라도, z로 길쭉하게 늘어선 장면(예: 긴 복도)에서는 한 타일의 near–far 사이가 넓어져, 실제로는 그 픽셀에 안 닿는 광원이 false positive로 목록에 끼기 쉽습니다. 이 깊이 방향 낭비를 없애려고 화면을 깊이까지 3D 셀로 쪼갠 것이 Clustered Shading입니다 — 다음 페이지(06-clustered)에서 이어집니다.

2. 직관 데모 — 타일 그리드에 광원 겹침 보기

아래는 화면을 타일 격자로 나눈 뒤, 각 타일이 겹치는 광원 수에 따라 색을 칠하는 히트맵입니다. 광원 하나는 영향 반경을 가진 원으로 그려집니다. 타일에 닿는 광원이 0이면 투명(계산 안 함), 많을수록 초록→노랑→빨강으로 뜨거워집니다. 슬라이더로 타일 크기와 광원 수를 바꿔 보세요. 타일을 잘게 쪼갤수록 타일당 평균 광원 수 k가 줄고(그만큼 픽셀당 조명이 싸짐), 대신 타일 수가 늘어(컬링 패스가 비싸짐) 트레이드오프가 눈에 보입니다.

타일 컬링 준비 중…
빨간 타일 = 그 타일 안 픽셀이 여러 광원을 도는 병목 타일. 투명 타일 = 광원 0 → 조명 계산 자체를 건너뜀. 이 "타일별 광원 목록"을 렌더링 전에 컴퓨트 셰이더로 미리 만드는 것이 라이트 컬링입니다.

3. Forward vs Forward+ vs Deferred

세 렌더링 경로를 광원 처리·타일 컬링·MSAA·투명·대역폭 축으로 비교합니다. 세 문단 설명보다 표 한 줄이 선택 기준을 더 또렷하게 보여줍니다.

경로광원 처리타일 컬링MSAA투명대역폭
Forward 픽셀마다 N개 전부 → O(P×N), 광원 많으면 폭발 없음 강함(하드웨어 MSAA 그대로) 강함(같은 패스에서 블렌드) 낮음(G-buffer 없음)
Forward+ 타일 컬링 후 픽셀은 k개만 → O(P×k), 많은 광원 OK 있음(컴퓨트 컬링 패스 추가 — 단점) 강함(포워드라 MSAA 유지) 강함(포워드라 투명 자연스러움) 중간(per-tile 광원 리스트 버퍼)
Deferred G-buffer 후 보이는 픽셀만 1회 → O(P×N)이지만 오버드로우 제거 선택(타일드/클러스터드 디퍼드로 확장) 어려움(G-buffer MSAA 까다로워 보통 후처리 AA) 약함(별도 포워드 패스 필요) 높음(넓은 G-buffer 읽고 쓰기)

핵심 대비: Forward+는 포워드의 장점(MSAA·투명·재질 자유도)을 그대로 유지하면서 디퍼드처럼 많은 광원을 감당합니다. 대가는 렌더링 전 컬링 컴퓨트 패스 한 번과 per-tile 광원 리스트 버퍼의 메모리·대역폭입니다. "많은 광원 + MSAA + 투명이 동시에 필요"할 때 디퍼드보다 유리한 이유입니다.

4. 구현 — 라이트 컬링 컴퓨트 셰이더 골격

컬링 패스의 핵심은 타일 하나 = 스레드 그룹 하나라는 매핑입니다. [numthreads(16,16,1)]이면 한 그룹이 16×16 = 256 스레드이고, 이 그룹이 화면의 16×16 px 타일 하나를 통째로 담당합니다. 그룹 안 스레드들은 groupshared 메모리로 협력합니다 — 타일 절두체를 함께 만들고, 광원 N개를 스레드끼리 나눠 검사하고, 통과한 광원 인덱스를 공유 리스트에 InterlockedAdd로 append합니다. 아래는 구조를 보여주는 골격입니다(그대로 컴파일되진 않고, 절두체 계산 등 일부는 요지만 표기).

light_culling.hlsl (컴퓨트 셰이더)hlsl
// ── 입력/출력 ──
StructuredBuffer<Light>  gLights      : register(t0);  // 광원 배열(중심+반경)
Texture2D<float>         gDepth       : register(t1);  // 이번 프레임 깊이(뷰공간 재구성용)

// per-tile 결과: [타일마다 (개수 + 최대 MAX개 인덱스)]로 평평하게 저장
RWStructuredBuffer<uint> gTileLightList : register(u0);

cbuffer CullConstants : register(b0) {
    float4x4 gInvProj;      // 클립→뷰 역투영 (타일 절두체 평면 계산용)
    uint2    gScreen;       // 화면 픽셀 크기
    uint     gLightCount;   // N
    uint     gTilePixels;   // 타일 한 변 픽셀 수(=16)
};

#define TILE       16
#define MAX_LIGHTS 256          // 타일당 담을 수 있는 광원 상한

// ── groupshared: 그룹(=타일) 내부에서만 공유되는 초고속 메모리 ──
groupshared uint  gsCount;                 // 이 타일에 담긴 광원 수(원자적 증가)
groupshared uint  gsIndices[MAX_LIGHTS];   // 통과한 광원 인덱스 목록
groupshared float gsMinZ, gsMaxZ;          // 타일 깊이 범위(near/far 평면용)

[numthreads(TILE, TILE, 1)]
void main(uint3 gid : SV_GroupID,          // 어느 타일인가(타일 좌표)
          uint3 dtid : SV_DispatchThreadID,// 이 스레드가 맡은 화면 픽셀
          uint  gi : SV_GroupIndex)        // 그룹 안 스레드 번호 0..255
{
    // 1) 대표 스레드가 공유 카운터 초기화
    if (gi == 0) { gsCount = 0; gsMinZ = 1.0; gsMaxZ = 0.0; }
    GroupMemoryBarrierWithGroupSync();     // ★ 초기화가 모두에게 보이도록 동기화

    // 2) 각 스레드가 자기 픽셀 깊이를 읽어 타일 깊이 범위를 원자적으로 좁힘
    float z = gDepth.Load(int3(dtid.xy, 0));
    InterlockedMin(gsMinZ, asuint(z));     // (실무는 float→uint 단조 인코딩)
    InterlockedMax(gsMaxZ, asuint(z));
    GroupMemoryBarrierWithGroupSync();     // ★ 깊이 범위 확정까지 대기

    // 3) 타일 절두체 6평면 계산 (요지):
    //    - 타일의 좌/우/상/하 화면 경계를 클립좌표로 만들고
    //    - gInvProj로 뷰 공간으로 되돌려 4개 측면 평면을 세운다
    //    - near/far 평면은 위에서 구한 gsMinZ/gsMaxZ로 좁힌다
    Frustum tile = BuildTileFrustum(gid.xy, gsMinZ, gsMaxZ, gInvProj, gScreen);

    // 4) 광원 N개를 256개 스레드가 나눠 검사 (그룹당 stride = 256)
    for (uint i = gi; i < gLightCount; i += TILE * TILE) {
        Light L = gLights[i];
        // 구(중심 L.posVS, 반경 L.radius) vs 타일 절두체 교차
        if (SphereInsideFrustum(L.posVS, L.radius, tile)) {
            uint slot;
            InterlockedAdd(gsCount, 1, slot);   // 통과 → 공유 리스트에 append
            if (slot < MAX_LIGHTS) gsIndices[slot] = i;   // ★ 오버플로 가드
        }
    }
    GroupMemoryBarrierWithGroupSync();     // ★ 모든 스레드가 append를 끝낼 때까지

    // 5) 대표 스레드가 groupshared 결과를 전역 버퍼로 flush
    if (gi == 0) {
        uint tileIndex = gid.y * ((gScreen.x + TILE - 1) / TILE) + gid.x;
        uint base = tileIndex * (MAX_LIGHTS + 1);
        uint n = min(gsCount, MAX_LIGHTS);
        gTileLightList[base] = n;                        // [0] = 개수
        for (uint k = 0; k < n; ++k)
            gTileLightList[base + 1 + k] = gsIndices[k];  // [1..] = 인덱스들
    }
}

4-1. 왜 groupshared + 배리어인가

  • groupshared는 같은 스레드 그룹(=타일) 안에서만 공유되는 온칩 초고속 메모리입니다. 256개 스레드가 하나의 광원 리스트(gsIndices)와 카운터(gsCount)를 함께 채우려면 전역 메모리 왕복 없이 여기서 협력하는 게 압도적으로 빠릅니다.
  • GroupMemoryBarrierWithGroupSync()는 "그룹의 모든 스레드가 여기까지 오고, groupshared 쓰기가 서로에게 보일 때까지 기다려라"는 동기화 장벽입니다. 초기화(1) → 깊이 범위 확정(2) → append 완료(4) 사이마다 필요합니다. 이걸 빼면 어떤 스레드는 초기화 전 카운터를 읽거나, flush가 append보다 먼저 실행돼 리스트가 비거나 뒤섞입니다.
  • InterlockedAdd(gsCount, 1, slot)는 원자적으로 카운터를 1 올리고 올리기 직전 값을 slot으로 돌려줍니다. 256개 스레드가 동시에 append해도 서로 다른 슬롯을 받아 충돌 없이 리스트를 채웁니다.

렌더링 쪽에서는 이 gTileLightList를 SRV로 읽어, 포워드 픽셀 셰이더가 자기 타일 광원만 돕니다. 아래가 그 소비 부분입니다.

forward_shade.hlsl (픽셀 셰이더, 타일 광원만 순회)hlsl
StructuredBuffer<Light> gLights       : register(t0);
StructuredBuffer<uint>  gTileLightList : register(t1);  // 컬링 패스가 채운 결과

#define TILE       16
#define MAX_LIGHTS 256

float4 main(float4 posH : SV_Position, PSIn i) : SV_Target {
    // 1) 이 픽셀이 속한 타일 좌표 → 타일 인덱스
    uint2 tileXY  = uint2(posH.xy) / TILE;
    uint  tilesX  = (gScreenX + TILE - 1) / TILE;
    uint  tileIndex = tileXY.y * tilesX + tileXY.x;
    uint  base = tileIndex * (MAX_LIGHTS + 1);

    // 2) 이 타일에 담긴 광원 수를 읽고, 그 개수만큼만 순회 (N이 아니라 k번!)
    uint  count = gTileLightList[base];
    float3 lit = i.albedo * 0.1;                 // 앰비언트

    for (uint t = 0; t < count; ++t) {
        uint li = gTileLightList[base + 1 + t];  // 타일 광원 목록에서 실제 인덱스
        Light L = gLights[li];
        lit += ShadeOneLight(L, i);              // 블린-퐁 등 한 광원 셰이딩
    }
    return float4(lit, 1.0);
}

핵심은 루프 상한이 전체 광원 수 N이 아니라 이 타일의 count(≈ k)라는 점입니다. 같은 코드가 광원 4개 타일에선 4번, 40개 타일에선 40번만 돕니다. 컬링이 잘 될수록 픽셀당 조명이 싸집니다.

함정 가장 흔한 두 실수입니다. (1) GroupMemoryBarrierWithGroupSync()를 빠뜨리면 초기화·append·flush의 순서가 보장되지 않아 어떤 프레임엔 광원이 통째로 누락되고 어떤 픽셀엔 쓰레기가 뜹니다 — 재현이 들쭉날쭉해 디버깅이 악몽입니다. (2) 타일당 광원 상한(MAX_LIGHTS) 오버플로: 광원이 한 타일에 몰리면 gsCount가 상한을 넘습니다. InterlockedAdd가 돌려준 slot이 상한 미만일 때만 쓰도록 반드시 가드해야 gsIndices 배열 밖 쓰기(정의되지 않은 동작)를 막습니다.
성능 Forward+의 병목은 광원이 밀집한 타일입니다. GPU는 타일(스레드 그룹)을 워프 단위로 굴리는데, 한 타일의 픽셀들이 count가 크면 그 워프 전체가 오래 붙잡혀 가장 빽빽한 타일이 프레임 시간을 지배합니다. 광원 반경을 실제 영향 범위로 타이트하게 잡고, 타일 near/far를 깊이로 좁혀 false positive를 줄이는 게 핵심 최적화입니다. 반대로 타일을 너무 잘게 쪼개면 절두체·컬링 오버헤드가 커지니, 16×16 안팎이 보통 균형점입니다.

5. 언제 쓰나 — 실무 노트

Forward+는 2012년 AMD의 Takahiro Harada 외가 정리하며 이름이 굳었고(내부 데모 "Leo/Leonardo's Day"에서 수천 광원을 타일 컬링으로 시연), 이후 많은 엔진이 채택하면서 "포워드 셰이딩의 부활"을 이끌었습니다. 디퍼드가 오랫동안 "많은 광원 = 디퍼드"의 공식을 만들었지만, Forward+는 포워드의 장점을 지키며 그 벽을 넘습니다.

실무
  • Unreal Engine은 모바일·VR 경로와 Clustered Forward(Forward+의 깊이 확장)로 많은 광원을 포워드에서 처리합니다. 데스크톱 기본은 디퍼드지만, MSAA·투명·VR이 중요한 프로젝트는 포워드 경로를 켭니다.
  • 모바일·VR에서 특히 선호: 하드웨어 MSAA를 그대로 쓸 수 있어 에지 품질이 좋고, 타일드 모바일 GPU의 대역폭 부담이 큰 G-buffer를 피할 수 있습니다. VR은 투명·안티앨리어싱이 몰입에 직결돼 포워드 계열이 유리합니다.
  • "많은 광원 + MSAA + 투명"이 동시에 필요한 씬이 Forward+의 결정적 스위트스폿입니다. 반대로 광원이 적거나(포워드로 충분) 깊이 복잡도가 극단적이면(디퍼드/클러스터드가 유리) 굳이 컬링 패스 비용을 낼 이유가 적습니다.

깊이 방향 false positive가 문제가 될 만큼 z로 복잡한 장면이라면, 화면을 깊이까지 3D 셀로 쪼개는 Clustered Shading으로 넘어가는 것이 자연스러운 다음 수순입니다.
